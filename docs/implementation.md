# Implementation status

Date: 2026-10-17. The original reviewed authoring interface is implemented; the simplification proposal was not adopted. The requirements/design files remain the reviewed target contract and are not rewritten to disguise gaps. This document describes actual implementation boundaries.

## Implemented surfaces

| Surface | Implementation |
|---|---|
| Configuration | Strict original inventory/fields/compatible_settings/policies schema, duplicate YAML detection, invalid preset/policy quarantine, content revisions, explicit source-refresh admission freeze. |
| Selection | Administrator-bound subagent policy, parent proposals, typed deterministic rules, fixed bindings, finite Jev preset/tuple Choice, bounded retries and explicit fallback graph. |
| Native plugin | Installed Python entry point, four public tools, lifecycle launch/status/cancel, exact deployment tuple checks, protected durable launch intent, native parent ownership checks. |
| Webhook | Plugin-owned API-server routes, raw-body HMAC authentication, typed body extraction/filtering before selection, original resolver, authenticated HTTP fresh-run submission. |
| Persistence | SQLite replay tombstones, stable scope across target changes, CAS/generation leases, cancellation fencing, startup/periodic recovery, bounded results/audit retention. |

| CLI | Offline `validate` and `inspect`; inspection expands complete provider/model/effort tuples. |
| Compatibility | A separately applied, pinned upstream patch adds public native per-launch effort and fallback suppression. The unpatched host rejects required effort. |

## Deployment configuration

An optional `--deployment` argument to `orpheus validate` validates this file offline. Unknown keys and malformed scope/tuple types are rejected. Top-level `redact_literals` applies to both entrypoints.

A separate administrator-owned YAML file supplies `subagent`, `targets`, `auth_profiles`, `operators`, optional `redact_literals`, and `jev_token_env`. It is not supplied by a task or webhook payload. All examples start with execution unverified/disabled.

Native `subagent.verified_settings` is an exact list of `{provider, model, effort}` dictionaries (omit effort only for an inheritance preset). These are operator assertions after deployment tests, not observations generated by Orpheus. Explicit effort additionally requires the patched public capability marker. Fallback is disabled per launch when the extension exists; otherwise the operator must verify fallback is disabled. Arbitrary provider strings are never accepted solely because a preset contains them.

Webhook targets bind an API origin, credential environment reference, principal identifier, allowed concrete model/provider/effort set, `verified`, and `fallback_disabled`. Local HTTP is allowed only for explicit loopback test targets; production origins use HTTPS and redirects are disabled. Target changes cannot reselect an admitted delivery. Model aliases, provider-specific effort, and fallback behavior must be included in target verification.

Auth profiles declare a stable default `scope`, an HMAC `secret_env`, and optional signature-header name (default `X-Hub-Signature-256`). A route may override this with a stable `security_scope`; effective scopes must be unique across routes. Operator scope grants use those exact effective scope names. The protocol supported here is body HMAC-SHA256 with a `sha256=` signature prefix. The full signed raw-body digest is the replay identity, independent of unsigned delivery headers. Identical legitimate bodies are collapsed; sources needing distinct identical-content events must include a signed unique value in the body. Replay tombstones do not expire. Operator configuration maps token environment names to permitted stable scopes; webhook signature secrets do not grant operator access.

## Explicit limitations

- This is not a claim that every proposed design extension is available. Fixed and enum fields with explicit static inventory/tuples are implemented. Free generation, discovered-inventory tuple generation, and dynamic instruction/tool fields are unsupported.
- The native effort source patch is not upstreamed, installed, or deployed. Its tests establish constructor arguments, not real-provider execution. Exact provider enforcement remains a deployment gate for both entrypoints.
- Native spawn awaits selection before returning its request ID. Cancelling the tool coroutine during selection prevents launch, but there is no separately exposed resolving-stage handle for a second tool to cancel. Host ownership expiration/restart makes old native results unavailable instead of returning data without ownership proof.
- Hot reload is not automatic. `Registry.refresh_yaml` supports explicit refresh and stale-source refusal, while the plugin requires reload/restart to install a new registry.
- Webhook auth initially supports body HMAC only. Header extraction, verified-metadata extraction, signed-time protocols, alternative signature algorithms and receipt adapters are unsupported and must not be silently accepted. Receipts must be disabled. Existing native routes are untouched.
- Webhook reconciliation polls known host IDs and supports administrative abandonment without inventing a terminal execution outcome. Original-host-ID attachment and automatic native idempotency replay are unsupported; unknown acceptance remains frozen rather than risking a duplicate.
- External result posting is not implemented. Operators retrieve bounded retained output through authenticated Orpheus status. Missing/expired host or local results remain unavailable/expired. Retrieval never reruns work.
- Provider settings are not dynamically probed with paid requests. Capability configuration is explicitly operator-attested and examples deny execution. No live Jev, provider, or installed Hermes gateway calls were made during development.

## Tests and review

Run `uv run pytest -q`, `uv build`, and `python compat/verify_patch.py`. Network-listening tests use only local aiohttp test servers. The compatibility verifier checks exact upstream fixture hashes, patch applicability and compilation; patched-function tests use stubbed external dependencies. Test source, fixture provenance and limitations are part of the implementation review packet.

Claude implementation review is recorded separately from the earlier design review. The design approval does not automatically approve this implementation.
